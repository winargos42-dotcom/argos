# Planeta v4: восстановление живого браузера из постоянной сессии

Дата: 2026-08-17

## Контекст

Planeta MCP v4 уже хранит зашифрованное состояние авторизации в
`/data/planeta/session.enc`, а рабочее состояние кампании — в доступном для
записи `/tmp/planeta_campaign.json`.

Текущий живой браузер, однако, создаёт постоянный профиль Chromium в
`/data/planeta/browser-profile`. Контейнер работает от непривилегированного
пользователя, а корень Railway-тома не разрешает создавать там новые каталоги.
Поэтому запуск завершается `PermissionError` до открытия Planeta.ru, хотя
сохранённая авторизация уже существует.

## Цель

1. Запускать графический Chromium только в доступном для записи временном
   каталоге.
2. Автоматически восстанавливать в нём зашифрованную авторизацию из
   `/data/planeta/session.enc` до первого открытия черновика.
3. Не требовать повторного входа, пока сохранённое состояние Planeta.ru
   действительно.
4. Не повреждать существующий `session.enc`, если Railway-том доступен только
   для чтения непривилегированному процессу.
5. Не менять защиту отправки на модерацию и не выполнять такую отправку.

## Не входит в объём

- запуск контейнера от root;
- изменение владельца или прав всего Railway-тома;
- ввод, хранение или автоматическая подстановка логина и пароля;
- обход CAPTCHA или другого подтверждения Planeta.ru;
- переработка селекторов редактора черновика;
- автоматическая отправка кампании на модерацию.

## Рассмотренные варианты

### 1. Временный профиль с восстановлением storage state — выбран

Зашифрованный `session.enc` остаётся постоянным источником авторизации, а
рабочий профиль Chromium создаётся под родительским каталогом
`PLANETA_STATE_PATH`, то есть на v4 — в `/tmp`.

До перехода на URL черновика браузер получает сохранённые cookies и допустимый
same-origin localStorage. Это использует поддерживаемую Playwright модель
storage state, но сохраняет графический persistent context, CDP и VNC,
необходимые для существующего живого моста.

Плюсы: не нужны привилегии, существующая сессия используется повторно, а
перезапуск контейнера безопасно удаляет лишь временный профиль.

### 2. Запуск от root или `chown` Railway-тома

Дал бы Chromium право создавать профиль на томе, но неоправданно расширил бы
привилегии контейнера и область возможного повреждения постоянных данных.

### 3. Новый ручной вход при каждом запуске

Технически обходит проблему профиля, но игнорирует уже сохранённую авторизацию
и возвращает одноразовые сессии, из-за которых возникла задача.

## Проект решения

### Разделение данных

- `config.session_dir / "session.enc"` остаётся постоянным зашифрованным
  источником Playwright storage state;
- живой профиль размещается в
  `config.state_path.parent / "planeta-live" / "browser-profile"`;
- состояние кампании и аудит остаются в существующих рабочих путях;
- headless-браузер продолжает читать тот же `session.enc` без изменения.

Новая переменная окружения не требуется. Для текущей конфигурации v4 это
означает постоянный файл `/data/planeta/session.enc` и временный профиль
`/tmp/planeta-live/browser-profile`.

### Запуск живого браузера

`LiveLoginCoordinator.start()` загружает storage state через `SessionStore` до
создания runtime и передаёт его фабрике живого браузера. Ошибка расшифровки или
валидации не скрывается: с повреждённой сессией браузер не должен запускаться
как будто авторизация корректна.

`LiveBrowserRuntime` получает необязательный storage state и выполняет запуск в
следующем порядке:

1. создаёт временный профиль;
2. запускает Xvfb, VNC и persistent Chromium context;
3. добавляет сохранённые cookies в context;
4. восстанавливает localStorage только для origin, который в точности совпадает
   с origin настроенного URL черновика;
5. лишь после восстановления переходит на URL черновика.

Cookies передаются в Playwright как валидированная часть storage state.
localStorage от посторонних и даже других поддоменов не восстанавливается.
Восстановление происходит до первой загрузки приложения Planeta.ru, чтобы оно
сразу увидело авторизованное состояние.

### Обновление постоянной сессии

После подтверждения авторизованного редактора coordinator получает актуальный
storage state из живого context и сначала пытается сохранить его существующим
атомарным механизмом `SessionStore.save_storage_state()`.

Если Railway-том разрешает запись, обновлённая зашифрованная сессия сохраняется
как обычно. Если создание временного файла для атомарной замены запрещено,
исходный `session.enc` остаётся нетронутым, а заполнение и сверка черновика
продолжаются с уже работающей живой сессией. Статус живого входа явно сообщает:

- `session_persisted: true`, если актуальное состояние записано;
- `session_persisted: false` и `session_persist_reason`, если сохранение
  невозможно.

Неатомарная перезапись существующего файла не используется: авария в середине
такой операции могла бы уничтожить единственную сохранённую авторизацию.
Следовательно, текущая сессия переживает перезапуски как постоянный источник,
но её обновление на томе зависит от реальных прав каталога Railway.

### Совместимость фабрик

Тестовые и пользовательские `runtime_factory` уже являются фабриками без
аргументов. Чтобы не менять этот контракт, coordinator после создания runtime
вызывает необязательный метод `set_storage_state(...)`. Стандартный
`LiveBrowserRuntime` реализует этот метод; отсутствие метода у внедрённой
внешней фабрики сохраняет прежнее тестовое и расширяемое поведение.

## Поток данных

1. MCP загружает и расшифровывает `/data/planeta/session.enc` в памяти.
2. Chromium создаёт профиль в `/tmp/planeta-live/browser-profile`.
3. Cookies и разрешённый same-origin localStorage восстанавливаются до открытия
   черновика.
4. Planeta.ru либо сразу показывает авторизованный редактор, либо возвращает
   проверяемое состояние `authentication_required`/CAPTCHA.
5. При доступном редакторе MCP заполняет и сверяет черновик.
6. MCP пытается атомарно обновить зашифрованную сессию; отказ записи не портит
   старый файл и не отменяет уже установленную авторизацию текущего браузера.
7. Runtime закрывается, а headless-браузер снова получает сохранённое состояние.
8. Отправка на модерацию остаётся отдельной операцией с одноразовым
   подтверждением владельца.

## Обработка ошибок

- отсутствующий `session.enc` означает обычный поток ручного входа;
- нерасшифровываемый или невалидный `session.enc` вызывает безопасный отказ без
  удаления файла;
- ошибка создания `/tmp/planeta-live` завершает запуск с точным типом ошибки;
- ошибка применения cookies/localStorage завершает запуск и очищает временный
  runtime, а постоянный файл не меняется;
- origin localStorage, отличный от origin черновика, игнорируется;
- отказ атомарного обновления сессии отражается в статусе, но не превращает
  успешно авторизованный и заполненный черновик в сетевую ошибку;
- неожиданный top-level origin после запуска по-прежнему блокирует захват
  сессии и заполнение.

## Проверка

Разработка идёт через падающие сначала тесты.

Модульные тесты проверяют:

1. стандартный live runtime использует рабочий каталог рядом с `state_path`, а
   не `session_dir`;
2. coordinator загружает существующий storage state до запуска runtime;
3. cookies применяются до первой навигации;
4. localStorage восстанавливается только для точного origin черновика;
5. без сохранённого состояния остаётся прежний поток ручного входа;
6. отказ атомарной записи не повреждает существующий `session.enc`, не отменяет
   заполнение и отражается в статусе;
7. успешная запись отражается как `session_persisted: true`;
8. ни один live-путь не вызывает `submit_for_moderation`.

После реализации запускаются сфокусированные тесты live browser/coordinator,
весь набор `tests/planeta_mcp`, компиляция и сборка Railway Dockerfile.

Проверка на v4:

1. `/health` возвращает 200;
2. live start больше не получает `PermissionError` для
   `/data/planeta/browser-profile`;
3. при действующей сохранённой сессии открывается авторизованный аккаунт без
   повторного входа;
4. черновик заполняется и синхронизируется без различий;
5. статус честно показывает результат сохранения обновлённой сессии;
6. отправка на модерацию не выполняется.

Если Planeta.ru уже аннулировала cookies в сохранённом файле, повторный вход
может потребоваться по решению самой площадки. Это устанавливается только после
фактической попытки восстановления, а не предполагается заранее.

## Откат

Откатить коммит реализации и повторно развернуть v4. Постоянный
`session.enc` не мигрируется и не меняет формат, поэтому отдельное
восстановление данных не требуется. Временный каталог `/tmp/planeta-live`
удаляется при перезапуске контейнера.

## Критерий готовности

Исправление готово, когда тесты и сборка проходят, v4 запускает живой Chromium
из доступного временного каталога, применяет существующую зашифрованную сессию
до открытия черновика, заполняет и сверяет кампанию без повторного входа при
действующих cookies и не отправляет её на модерацию.
